# fs-hub – Design

`fs-hub` is the FreeSynergy hub (ADR 0019): **one small daemon per device**. Programs never look for each other, only for the hub.
The hub collects the objects of all programs in its own `fs-store`, keeps a cursor per program, and proposes matches.
It contains only connecting logic, no domain logic. Programs work alone without it and hand over their log later.

## Structure and pattern map (ADR 0043)

Every file is one concept, <= 200 lines (tests included; e2e tests split by feature in `crates/fs-hub/tests/`, helpers in
`tests/common`), `lib.rs`/`mod.rs` only declare and re-export, every module doc has a `Pattern:` line. Programs depend
on traits; concrete types are wired in `core/hub.rs`.

## Crates

* `fs-hub-proto`: re-export of the contract from `fs-interfaces`, conversions wire <-> `fs-store` types. A third crate beyond the two asked for, so daemon and client share the contract without depending on each other.
* `fs-hub`: `HubCore` (connecting logic, no RPC, behind the traits `ProgramRegistry`, `ActivitySink`, `ActivitySource`, `ProposalEngine`, `CursorRepository`), `server` (RPC adapter), `Daemon` (own thread, for tests/embedding), binary.
* `fs-hub-client`: what programs embed.
* Dependencies: `capnp`/`capnp-rpc` 0.27 (MIT), `fs-interfaces` (git tag v0.44.0, feature `rpc`), `tokio`, `tokio-util`, `futures`, `serde`, `tracing`, `fs-store` (git tag v0.4.0).

## Decisions

* **Hub log = delivery log.** The hub applies a pushed object change with `store.put/delete`; its own activity log (UUIDv7) is what `pull` reads. The hub activity's `actor` is the **program name** (the original actor string stays only in the program's log). A program therefore never receives its own changes. On the receiving side the actor is written as `hub:<program>`.
* **Wire format.** `Activity` carries the typed `Envelope` (routing summary) and the full before/after images as JSON `payload` (domain content is JSON in the standards anyway). `common.capnp`'s `Envelope` now carries `describes`, `startTime`, `endTime` (fields @15-@17, schema copy updated, code regenerated); `write_envelope`/`read_envelope` map them. The JSON payload still carries the complete images and stays authoritative for content.
* **Cursors.** Push: the program's own log is the cursor (`last_accepted`); a bad single entry is reported in `problems` and the cursor moves past it (one bad entry must not block the log). Pull: `since` zero = hub-kept cursor; `pull` does not move it, `ack` does, so a crash between apply and ack only repeats work (applying is idempotent: identical content is skipped).
* **No echo.** Entries the client wrote while applying pulled changes have the actor `hub:<program>` and are never pushed: `push_all` passes them and marks them synced. Pushing one could roll the hub back, since it may hold a newer version by then; that can happen after a crash and behind a foreign unsynced entry, because `mark_synced` acknowledges a prefix. Identical content is still skipped at the hub. `HubSession::push` is not filtered: it sends what it is given.
* **A failure that may pass moves no cursor.** A bad entry (not a change set, refused by a store rule) is reported and passed. A backend or key error is nothing the entry did: the hub keeps what it applied, stops with an error and the cursor in front of the entry; `sync_once` acknowledges what it applied and stops. Problems reported earlier in such a failed push are lost with it. Only a lost `originalAt` does not stop anything. `sync_once` then returns `Error::Stopped` with the report so far, including entries already passed. Hub state is saved before every answer to a push, so what it acknowledged stays acknowledged across a crash, and a program that lost its own mark and pushes again overwrites nothing (`crash_replay`); only the compaction of `state.db` and `times.db` waits, at most a second.
* **One bad program cannot see more than it declared**: `reads` filter on the hub side. `writes` is enforced too (undeclared types are `withheld`).
* **Proposals only across programs.** Duplicates inside one program are that program's own business (`fs-people-core` finds them). The hub only proposes; a human confirms in a program, which writes the `Relationship` (`owl:sameAs`) that the hub then respects.
* **Hub store is unencrypted** (no key vault yet), which is why sensitive objects are refused instead of stored.
* **A sensitive object says only that it is.** Each image is looked at on its own: a sensitive one travels as a stub with its id, a generic marker, a neutral name and type, zero times; the entry's `at` is zero and `actor` blank on every push. The other image of the same change stays, or taking a mark off would destroy the object. What goes depends on the object as it is now: of an object marked now, all images of its unsynced history go as stubs, so the plain past stays on the device as well. A log-only entry about a sensitive object, or one the store no longer has, does not leave the program and counts as withheld. **UUIDv7 ids hold their creation time**, of the object and of the entry, also on a stub's push and on a delivered delete: that is a limit of the id format, not something this can blank.
* **An entry without state is no deletion (fs-store 0.4).** After `purge_object`, later writes of the object are logged as `{"redacted":true,"before":"redacted","after":"redacted"}`. The hub skips such an entry (counted as skipped, no problem, the cursor moves on, its copy stays), nobody is entitled to its type (invisible), a feed never tells it, and a client that pulls one changes nothing. The hub cannot fetch the object (it has no access to the program's store), so the *client* does it when pushing: the entry keeps its id and goes as an `Update` with the object's current copy (marked objects as stubs, as always), or as a `Delete` if the store no longer has the object. Only a real `Delete` entry removes a copy.
* **Marked later (PROVISIONAL, strategy session 2026-11-06).** A mark set in a program takes the object off the hub only; it never deletes another program's object. When a mark reaches the hub, with or without a copy there, the object goes on a persistent list (`core/marked.rs`), and everything logged about it so far is covered. A covered `Create`, `Update` or log-only entry passes as invisible. A covered delete goes to readers as a plain `Delete`: no payload, a neutral envelope, no marker, `at` zero, `actor` blank, no time. Readers carry it out on their copies. The program that first wrote the object does not get it, and no client deletes or overwrites a local object that is marked there. Times are forgotten before the list closes, and `times.db` keeps no history. The order is: list open, delete, forget, list closed; after a crash the same push comes again and finishes it. A notice waiting in a feed's queue is checked again when its turn comes.
* **Preconditions of `purge_object` (ADR 0029).** (1) **Sync first, then purge.** A purge deletes the unsynced log entries too: a program that marks an object and purges before the next sync leaves the hub with the unmarked copy and nothing to push the mark with (measured; `PurgeReport.unsynced_removed > 0` is the signal, tested in `fs-hub-e2e/tests/purge_sync.rs`). So a program never calls `purge_object` itself: it calls `HubSession::sync_then_purge(store, id)` (`HubStatus::sync_then_purge` too), which syncs, checks that no entry of the object is left unsynced (the hub may hold some back) and only then purges. No hub, a failed sync or entries left behind: nothing is purged (fail closed; `Error::NoHub`, `Error::Stopped`, `Error::NotSynced`). A write between the check and the purge is not covered: look at `unsynced_removed` in the returned report. (2) **A mark can be lifted after a purge, but only by the program that can know it.** The owner's next push has no `before` image, so it proves nothing about a mark. A change of kind `Update` without `before` lifts only for the program that set the mark (`removal.by`, the owner too when it set it itself); the owner does not learn of another program's mark (`marked.rs`), so its unmarked copy must not undo that: its write is held (counted as withheld), its own store is untouched, the object only stays off the hub. With a `before` image that is marked, the rule is as before (owner or marking program). Tested in `purge_mark.rs`, including `sync_then_purge` after a foreign mark. An explicit lift for the held case (a hub call with proof) is a point after the sprint.
* **Known gap: deleted, then marked, then purged.** `was_marked_later` (`fs-hub-client` `sync/push.rs`) reads the images of later entries; after a purge they have none, so such an object goes as a normal `Delete` with its original time instead of as a stub, which tells when it was deleted. The content is not sent. Not fixed yet.
* **While a mark holds (strategy decision, 2026-11-06).** The owner (the program that first wrote the object) and the program that set the mark can lift it, with a change whose `before` image is sensitive, and nobody else; any other unmarked put is refused with a problem (409) and the cursor moves past it, so a stale copy cannot bring the secret back. No program can take the owner's own data (it keeps it and writes on); but a mark set by another program keeps the object off the hub until that program lifts it or an explicit lift exists (open points below). Program names are not authenticated (ADR 0035). The owner keeps its data and goes on writing while the mark holds; the object just stays away from the hub. Those writes are not refused, not lost and not counted as delivered: they count as withheld, and `lastAccepted` stops in front of the first of them (`ProgramState::held`, persisted). `mark_synced` takes a prefix of the log, so that entry and everything behind it stay unsynced and go again on each sync; the hub skips what it has. So a long hold costs the owner a growing resend, which a selective `mark_synced` in `fs-store` would remove.
* **Who may lift a mark (strategy decision, 2026-11-06, in the code and tested: `mark_owner`, `mark_rights`).** Only the owner and the marking program, the owner only if it proves it knows the mark (a marked `before` image) or set it itself; no program can lock the owner out for good (its writes wait, they are not refused); the object only stays away from the hub, the owner keeps its data. A Delete removes the copy at a reader (`fs-hub-e2e/tests/collect.rs`). `email` and `phone` in the delivered index go only on a `Profile` to a program that may read cards, never of a marked card (ADR 0029 point 1; `delivery/tests.rs`, `collect.rs`).
* **When a mark lifts, the owner's object wins.** The owner's writes come through on its next sync, the newest last. What the marking program brings along when it lifts stays out, because it may be older than what the owner holds, which the hub cannot tell. So after such a lift, an owner that wrote nothing meanwhile has no copy at the hub until it next writes; the old version is not brought back from the log. "The person" as a third party who may lift a mark comes with verified callers: today any process of the user can claim any program name.
* **Rights.** A delete, a marked removal and a put need the type of the hub's copy (or, without a copy, of the log's last image) in the program's `writes`; a put needs its own new type there as well, or naming another type would get round this. Otherwise they are withheld and nothing happens.
* **The list must not go missing.** `state.db` holds a marker from the moment `marks.db` exists; the marker without the file stops the hub from starting (`Error::MarksLost`). Over a log without a list, from an older hub, every object whose last entry is a delete is listed conservatively (`holds: false`), since a marked object looks like any deleted one then, and an ordinary delete of that time loses its old entries for later readers. Each entry keeps the object's origin itself, as the log it comes from will be purged. If both files are lost, this conservative listing runs again. At start a mark that holds with a copy here (`marks.db` newer than a restored `objects.db`, or a crash) finishes its removal, and `proposals` name nobody a mark holds.
* **Limit, plainly: the old content of a marked object is still on the hub's disk**, in the log of `objects.db`, including the delete's `before` image. It is only not delivered. **The purge of a marked object's old log entries waits for the log purge API `fs-store` is getting.** Until then `marks.db` is all that keeps it from going out.
* **Blanked at delivery (PROVISIONAL, strategy session 2026-11-06).** The cores set `attributedTo` and `to` to the person's IRI (`fs-people`, `fs-wiki`, `fs-calendar`), which would tell every reader what `originalActor` keeps back. So `attributedTo`, `to`, `cc`, `bto`, `bcc`, `audience` are blank in everything that leaves the hub: the typed envelope, the envelopes inside the images, live notices. `actor` is blank on push. `original` (an rfc822 original can hold a `Bcc:`) and the payloads of log-only entries are not delivered to other programs either, and an image only keeps the index keys a reader needs (`DELIVERED_INDEX_KEYS`, an allowlist: a new key stays home until somebody adds it). `email`, `phone`, `nickname` and `org` go only on a `Profile`: they say what the card says, to programs allowed to read that type anyway, never of a marked card (ADR 0029 point 1). `subject` goes only on a `Relationship`, where it is a card id, not a person's IRI; `fs-resources` uses the key for something else. Content such as a JSContact card stays, since it is the object itself; so do `iri`, `context` and `describes`, which is open. One place: `fs-hub-proto/delivery.rs`, because a later release per person and per program will control these same fields.
* **Who decides those fields.** The program that first wrote the object (`origin_of`) is authoritative: its push always overwrites them and any difference counts as a change, so a person can remove a recipient. From any other program they are blank, which is kept: the hub keeps its values (`keep_held_back`), and a client keeps its own when it pulls, so a blanked object going round overwrites nothing, and it is no change (`same_content`).
* **Last write wins.** A pull passes entries older than the program's own entry about the same object in the hub's log. Otherwise two concurrent edits differ for good: the hub would hold the later, the later writer the earlier.
* **`originalAt`: the time the program did it.** Sent with the push, kept in `state.db` by the id of the hub's log entry (the store sets the log's own `at`), delivered with `pull`, so `at` stays the time the hub applied it. Never for a withheld or sensitive object (ADR 0029): the client does not send it, the hub keeps none for such an entry, also not for the delete that removes an older copy, and does not deliver one. Written after the change, not in one transaction: a crash in between loses only the time.
* **`originalActor` stays empty and the hub delivers it to nobody** (strategy decision, 2026-11-06). Who did something can only be released by the person; a manifest cannot grant this, since a program would be granting it for itself. The hub neither reads nor stores the field, whatever a program sends. `actor` remains the program's name.
* **`Lagged` ends the feed.** A lagging program could catch up with `pull`, but the contract only has `ended` to tell it that changes were missed, and a feed must never end silently. So it ends; the program subscribes again and then pulls, in that order.

## Limits

A message above the reader's limit ends the whole connection with all its capabilities, so nobody may send one. All in `fs-hub-proto/limits.rs`:

| Limit | Value | Why |
|---|---|---|
| `rpc::MAX_PAGE_BYTES` | 32 MiB | a pull answer and a push piece end before the next activity would pass it; at least one activity, so paging advances |
| `MAX_OBJECT_BYTES` (`rpc::MAX_INTAKE_BYTES`) | 16 MiB of JSON per image | the same limit every server has |
| Largest allowed activity | 48 MiB | two images and the envelope summary |
| `MAX_HUB_MESSAGE_BYTES` (2 x `rpc::MAX_MESSAGE_BYTES`) | 128 MiB, `ReaderOptions` on both sides | holds the largest allowed activity with room to spare, and any entry an older hub could have logged up to about this size |

* **Weight, not count.** An activity weighs its JSON payload, so an update counts its object twice, plus `rpc::envelope_weight` and a fixed frame. The count limit (`limit`, default 200, at most 1000) still applies. The cursor logic is unchanged: an answer ends before the activity that does not fit, `last` is the last one scanned before it, `more` says one is waiting.
* **Above the limit at push.** The hub checks the `after` image (log-only: the payload) after the sensitive and `writes` rules, reports a problem of type `too-large` (413), and the cursor moves past it, as for any bad entry. The hub keeps its older version of that object until a smaller one comes; the pushing program is the one told, readers are not. `HubSession::push` checks too, because an object above the message limit could not reach the hub at all: the entry stays home, the outcome has the same problem and `last_accepted` moves past it. There an undeclared large type counts as a problem, not as `withheld`, since the client does not know the rule. A large `before` image is left out: the hub keeps its own.
* **Above the message limit in the hub's log.** Only an entry older than these limits can be. It goes without `before`, which a reader does not need. If `after` alone is too large, it goes with an empty payload, so its reader moves past it: `sync_once` reports it in `failed`, `envelopeOnly` still shows what it is. A delete is carried out with or without a payload.
* **Memory.** The store cannot filter by size, so hub and client read a sliding window: it grows by one with each small entry up to 16, and an entry of 256 KiB shrinks it to one again (`ScanSize`). Envelopes are read from the JSON without copying the content, payloads are taken, not cloned; no store change was needed. Measured on the real binary, a page of 28 MiB (entries of 14 MiB): peak 169 to 183 MiB across runs, 981 MiB with 32 entries at once. A push of 1000 small entries on the same disk: 12.6 s, saving before each answer with compaction at most once a second; 17.3 s at the first version of the size cut; 31.8 s compacting on each call.
* **Summaries do not move the cursor.** The hub's cursor means "the content up to here is applied". `pull_envelopes` gives its own `EnvelopeCursor`, a type `ack` does not take (checked by a `compile_fail` doc test), and the hub does not remember it. On the wire `ack` is one method, so a session remembers how far its full pulls got and refuses an `ack` beyond that. A session cannot acknowledge what an earlier session pulled: pull again.

## Not done yet

* **Socket activation** (systemd `.socket` unit / starting the hub on demand). Today the hub is started by hand.
* **Installing the hub on demand**: `offer_install()` only returns text.
* **mDNS / DNS-SD, names, domains, ACME, WebFinger** (ADR 0028).
* **OpenID Federation, P2P, instance-to-instance sync** (ADR 0035, 0036).
* **Authentication of the socket peer** beyond "same uid": no program identity proof (any process of the user can claim any program name), no encryption of the socket (local Unix socket, so none on the wire), no per-program tokens.
* **Encrypted hub store** and the key vault (ADR 0024); explicit per-recipient release of sensitive data (ADR 0029 point 2). Until then sensitive data stays in the program.
* Windows named pipes; JSON/HTTPS, CLI and MCP faces generated from the schema (ADR 0021).
* Hub-side log compaction/retention (the hub log only grows; `state.db` is compacted); tombstones for deleted objects of programs that were offline long.
* Conflict handling: concurrent edits of one object in two programs are last-write-wins at the hub (ADR 0020 "Konfliktzustand" is open).
* Addressing (`to`/`cc`) is kept at the hub but not used for filtering, and not delivered for now.
* The calendar-participant -> contact link is not made by the hub; the calendar finds the pulled contact by e-mail itself.
* Limits: batch sizes are fixed (pull 200 default), all limits above are constants; `Activity.at` travels with millisecond precision. After a run of small entries, a scan can hold 16 entries of any size.
* `proposals` is on `Hub` in the contract, without a session, so the hub filters by what the same connection registered, and an unregistered connection gets none. It belongs on `Session`; the contract should move it. Not cut by size either: names up to an object's size, in numbers, could pass a message. Nothing near that has been seen.
* **Server transport not on `rpc` yet**: the client uses `rpc::connect_with`, which refuses a socket served by another user. `rpc::serve_with` hands one bootstrap to every connection and `BoundSocket`'s listener is private, while `proposals` is on `Hub` in the contract, without a session, so the caller is only known from a per-connection bootstrap. Moving now would give names and e-mail addresses to any caller. Once `proposals` is on `Session`, the hub drops its accept loop and `bind_socket`, and gets the lock file and the euid check of `rpc`; until then a start racing another start is not excluded. Taken from `rpc`: envelope, uuids, default socket path, feed forwarding, `Problem`, limits, `connect_with`, `prepare_data_dir`.
* A consumer whose `change` never returns only stops the feed for itself; `ended` cannot overtake that call (see Needed elsewhere), and if the feed lagged meanwhile nothing more arrives to trigger the overflow rule. It ends with the connection.

## Needed elsewhere

* **`common.capnp` `Envelope`**: done (`describes`, `startTime`, `endTime`). Open: `iri` nullable semantics ("" = none is used now).
* **fs-store**: (a) `Store::put` always stamps `updated`/creates a new activity; a "apply remote change without a new local log entry as unsynced" (or `put_synced`) would remove the need for the `hub:` actor convention; a log purge is coming, and the old entries of a marked object wait for it; a size column in `ActivityFilter` would let a scan stop before reading a large entry; (b) `ActivityFilter` has no object-type filter, so the hub reads and parses payloads to filter by type; (c) `mark_synced` is prefix-only; (d) an `ObjectId` can only be UUIDv7, so the hub cannot derive deterministic ids for its state objects.
* **fs-contacts**: index `kind`, `email`, `phone` are read by the hub's proposals; they should be documented as part of the hub contract (the hub knows these index keys). Better: a generic "identity keys" index convention in `data/<domain>/standards.md`.
* **fs-calendar**: `Event` participants are only e-mail strings; a hub-level "participant -> contact" resolution would need a convention for which index key carries identity (`participant_email` vs contacts' `email`).
* **`fs-interfaces`**: `proposals` belongs on `Session` in `hub.capnp`, see above. Since v0.43.0 `rpc` is on `fs-store` v0.4.0, as the hub is.
* **`fs-history-hub`**: pins hub v0.2.0. At the next bump `DEFAULT_MAX_BATCH` and the "too large" advice can go, `pull_envelopes` fits it (it reads only summaries), and `tests/large_batch.rs` expects the old failure.
* **ADR 0019** names the socket but not the contract version negotiation: 0.1 requires an exact match for now.

## Open (review of 0.3.0)

Partly there before 0.3.0. Needs a lock per object or one transaction over marks and objects.
